# Kodhane v4.4 — Paket B runbook: aşama ID eşlemesi + sürüm koruması

Ön koşul: Kodhane v2.2 ve **Paket A** canlıda (migration ikisini de kontrol eder, yoksa durur).
Sıra: **A → v4.4 istemcisi yayında → B**. Geri alma sırası: B → A. Veri yazmaz, backfill yok.
`kodhane_leaderboard` (v6) ve Açık Ofis nesnelerine dokunmaz.

Dosyalar:
- `supabase/migrations/20260929204000_v4_4b_kodhane_stage_ids_version_guard.sql`
- `supabase/rollback/20260929204000_v4_4b_kodhane_stage_ids_version_guard.rollback.sql`
- `supabase/ops/v4_4b_preflight.sql` (READ ONLY: hedef, v2.2, A, B durumu, saklı saveVersion dağılımı → hangi istemci reddedilir)
- `supabase/ops/v4_4b_verify.sql` (READ ONLY: 7 kontrol, hepsi `t`)
- Testler: `supabase/tests/v4_4/run_v4_4b_tests.sh` (+ `v4_4b.test.sql`, `http_v4_4b.sh`; yerel docker, canlıya bağlanmaz)

## Ne ekler
- `kodhane_saves.best_stage_id text` (NULL = `best_stage`'den türet) + check `kodhane_saves_best_stage_id_known`.
- Trigger `kodhane_saves_v44_stage_id` (BEFORE INSERT OR UPDATE): `best_stage_id` = max(eski, legacy(best_stage),
  denetlenmiş kayıt ID'si). Düşmez; yalnız `kodhane_score_plausible` geçen kayıttan gelir. İstemci bu kolonu yazamaz
  (kolon UPDATE yetkisi yok), elle SQL de yazamaz (trigger yeniden hesaplar).
- Trigger `kodhane_saves_a_version_guard` (BEFORE UPDATE, v2.2 trigger'ından önce çalışır): kural
  `sv_new < sv_old and sv_old >= 5`. Saklı kayıt v4.4 biçimindeyse (`saveVersion` ≥ 5) ve gelen `data.saveVersion`
  (yok / sayı değil = 0) ondan küçükse **SQLSTATE PT426 → HTTP 426**, message `save_version_too_old`,
  detail `sent saveVersion X, stored saveVersion Y`. Satır değişmez.
  Biçim 4 kayıtlar (v4.3.0 / v4.3.1) korunmaz: iki istemci aynı biçimi yazar, v4.3.0 sekmesi (saveVersion göndermez)
  v4.3.1 kaydının üzerine yazmaya devam edebilir.
  Yalnız `data.saveVersion` okunur, `data.version` okunmaz: v4.3.0 yüklediği v4.4 kaydının `version` 5'ini korur ama
  v4.4 alanlarını (veri/cip, aşama ID'leri) siler; `version`'a bakılsaydı bu yazma geçerdi.
  Muaf: `postgres`, `supabase_admin`, `service_role` (elle SQL, service key, reset/restore RPC'leri).
- RPC `kodhane_leaderboard_v7(p_limit)`: v6 Kodhane listesi + `stage_id`. v6 aynen kalır.

## Uygulama
```bash
psql "$DB_URL" -X -v ON_ERROR_STOP=1 -f supabase/ops/v4_4b_preflight.sql > b-preflight.txt
psql "$DB_URL" -X -1 -v ON_ERROR_STOP=1 -f supabase/migrations/20260929204000_v4_4b_kodhane_stage_ids_version_guard.sql
psql "$DB_URL" -X -v ON_ERROR_STOP=1 -f supabase/ops/v4_4b_verify.sql     # 7 satır t
```
Preflight'ta saklı saveVersion dağılımına bak: yalnız `sv ≥ 5` (v4.4 biçimi) olan hesaplarda v4.3.x ve daha eski
istemciler yazamaz (426); `sv ≤ 4` hesaplarda her istemci yazar. B v4.4 istemcisinden sonra uygulandığı için uygulama
anında `sv ≥ 5` grubu yalnız v4.4 ile oynamış hesaplardır. Beklenmedik büyüklükte grup varsa uygulama, Product'a sor.

## İstemci sözleşmesi
- **426 / PT426**: tekrar deneme; "Oyunun yeni sürümü var, sayfayı yenile" göster. Yerel kayıt korunur, bulut ezilmez.
  v4.1.1 / v4.3.0 / v4.3.1 426'yı tanımaz: genel hata mesajı + ~45 sn'de bir yeniden deneme (sekme başına, backoff yok).
  Bu artık yalnız **v4.4 biçimindeki (saveVersion ≥ 5) bir kaydın üzerine** yazmaya çalışan eski sekmede olur (ör. aynı
  hesap başka cihazda v4.4'e geçti, eski sekme açık kaldı). Zararsız ama gürültülü. v4.4 istemcisi 426'yı işler
  (`update.olderTab.*` bandı, tekrar yok).
- **409** (revision çakışması) davranışı değişmez. Ayrı kod bilerek seçildi: v4.3.0 409'da reconcile yapar ve v5 kaydı
  veri/cip ve aşama ID'leri silinmiş haliyle geri yazardı.
- **v7**: yeni aşama adlarını göstermek için istemci `kodhane_leaderboard_v7` çağırıp `stage_id` kullanmalı; 404 (B yok
  ya da geri alınmış) olursa v6'ya düşmeli. v4.4.0 v6 `stage` kullandığı için Unicorn / Şirketler Grubu'nu
  Global Holding gösterir (yanlış değil, eksik).

## Elle düzeltme
- Admin SQL sürüm korumasından muaf. v2.2 revision kuralı geçerli: güncellemede `revision = revision + 1` ekle.
- `best_stage_id` elle yazılamaz (trigger hesaplar). Zorunlu durumda trigger'ı kısa süre kapat, tek satır düzelt, aç.
- Acil kapatma (yalnız sürüm koruması): `alter table public.kodhane_saves disable trigger kodhane_saves_a_version_guard;`
  Geri açma: `... enable trigger kodhane_saves_a_version_guard;`
- Sıfırlama sonrası saklı saveVersion 0 olur; o hesapta her istemci yeniden yazabilir.

## Geri alma
```bash
psql "$DB_URL" -X -1 -v ON_ERROR_STOP=1 -f supabase/rollback/20260929204000_v4_4b_kodhane_stage_ids_version_guard.rollback.sql
```
Trigger'lar, yardımcı fonksiyonlar, v7, check ve `best_stage_id` kolonu silinir. **`best_stage_id` verisi kaybolur**
(yeniden uygulamada NULL'dan başlar; `best_stage`'den türetilir, yeni aşamalar bir sonraki geçerli kayıtta geri gelir).
v7 çağıran istemci 404 alır → v6'ya düşmeli. A'yı geri almak için önce B geri alınmalı.

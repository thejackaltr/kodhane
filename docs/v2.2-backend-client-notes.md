## Sunucu sözleşmesi (Açık Ofis; Kodhane birebir aynı, yalnız önek `kodhane_`)
### Sütunlar (`acik_ofis_saves`)
- `revision bigint`: istemci yazar (kurallar aşağıda).
- `best_score numeric`, `best_stage int`, `strict_revision boolean`: **yalnız sunucu yazar**, istemci okuyabilir
  (yazmaya çalışmak 403 / 42501). `best_score` = şimdiye kadarki en yüksek *makul* (plausible) `totalEarned`;
  `best_stage` = makul kayıtlardaki en yüksek `data.stage` (0..99'a sıkıştırılır, sayı değilse 0). İkisi de hiç düşmez,
  sıfırlamadan sonra kalır, yedeklerde saklanır (satır yeniden oluşursa yedeklerden geri gelir).
- Okuma: `GET /rest/v1/acik_ofis_saves?select=data,save_version,updated_at,revision,best_score[,best_stage]&user_id=eq.<uid>`.

### Yazma (upsert) ve revision kuralı
İstemci gövdeye `revision` koyar. Sunucu (trigger) şöyle karar verir; "eski revision" = satırdaki değer:

| Durum | Sonuç |
|---|---|
| Satır yok (INSERT) | Kabul. `revision` = gönderilen (yoksa 0). Gönderilen > 0 ise satır baştan **strict**. |
| `revision` < eski | **409** `PT409` `stale_revision` (her zaman). |
| `revision` = eski (ya da hiç gönderilmemiş, yani eski istemci), satır **strict** veya `revision_mode = 'strict'` | **409** `PT409` `stale_revision`. |
| `revision` = eski, satır **lenient** (`strict_revision = false`), `totalEarned` düşmüyor | Kabul; sunucu `revision = eski + 1` yazar, satır **lenient kalır**. |
| `revision` = eski, satır lenient, `totalEarned` düşüyor | **409** `PT409` `stale_write` (hatanın kendisi: sıfırlanmış boş kaydın gerçek ilerlemeyi ezmesi). |
| `revision` > eski (aradaki boşluk fark etmez) | Kabul; satır **strict** olur ve öyle kalır. |

- **Satır ilk açık artan revision'la strict'e geçer. Buna `acik_ofis_reset_save` ve `acik_ofis_restore_save` de dahil:**
  ikisi de satırı `revision = eski + 1` ile günceller, trigger bunu artan revision sayar → satır strict olur.
  Satır yokken restore, satırı `revision = yedeğin revision'ı + 1` (≥ 1) ile oluşturur → yine strict.
  Strict'ten lenient'e dönüş yok.
- Sonuç: bir oyuncu sıfırladıktan (veya v2.2 istemcisi bir kez yazdıktan) sonra, o hesabın **eski (v2.1.x) istemcileri**
  her yazmada 409 alır (kayıt yapamaz, buluttaki kayıt korunur). Güncelleyene kadar o cihaz fiilen salt okunur.
- `revision_mode` (`acik_ofis_game_config`, varsayılan `lenient`) `strict` yapılınca eşit revision her satırda reddedilir.

### RPC'ler (hepsi `POST`, girişli kullanıcı, `auth.uid()`; `game` alanı **yok**)
| RPC | Gövde | Dönüş |
|---|---|---|
| `rpc/acik_ofis_reset_save` | `{}` | `{revision, backup_id, best_score, best_stage}` |
| `rpc/acik_ofis_restore_save` | `{"p_backup_id":"<uuid>"}` | `{revision, backup_id, restored_from, best_score, best_stage}` |
| `rpc/acik_ofis_list_save_backups` | `{}` | `[{id, revision, reason, score, best_score, stage, best_stage, created_at, expires_at}]` (yeniden eskiye) |

- Reset: satır silinmez; önce yedek (`reason = 'reset'`), sonra ilerleme temizlenir, `revision = eski + 1`. `best_score`,
  `best_stage`, takma ad ve hesap kalır. **Satır yoksa satır oluşturmaz: `{revision: 0, backup_id: null, best_score: 0, best_stage: 0}`.**
- Restore: yalnız kendi, 30 günden yeni yedeğin; revision kontrolü yok. Önce mevcut durumu yedekler (`reason = 'restore'`,
  dönen `backup_id`), yani geri yükleme de geri alınabilir. Başkasının ya da süresi geçmiş yedek: **404** `PT404` `backup_not_found`.
- **Restore oyun verisini döndürmez**, yalnız meta bilgi döner: `revision`, `backup_id`, `restored_from`, `best_score`,
  `best_stage` (`acik_ofis_restore_save` ve `kodhane_restore_save` aynı; SQL'deki `jsonb_build_object` ile teyitli).
  Restore'dan sonra istemci satırı yeniden çekmeli
  (`GET …?select=data,save_version,updated_at,revision,best_score,best_stage&user_id=eq.<uid>`) ve yerel state'i onunla
  değiştirmeli; `L` = çekilen satırın `revision`'ı (RPC'nin döndüğüyle aynıdır).
- Oyuncu başına en çok 50 yedek (eskiler budanır), 30 gün saklama.

### Hata kodları → HTTP (yerel Supabase yığınında HTTP testiyle gözlendi)
| Durum | code / message | HTTP |
|---|---|---|
| Küçük revision; ya da strict satırda / strict modda eşit (veya gönderilmemiş) revision | `PT409` / `stale_revision` | 409 |
| Lenient satırda eşit (veya gönderilmemiş) revision ile totalEarned düşüyor | `PT409` / `stale_write` | 409 |
| Başkasının / süresi geçmiş / olmayan yedek | `PT404` / `backup_not_found` | 404 |
| Girişli kullanıcı: DELETE, `best_score`/`best_stage`/`strict_revision` yazma, başkası adına INSERT (RLS) | `42501` | 403 |
| Anon: kayıt/yedek tablosu, reset/restore/list RPC'si | `42501` | 401 |
| Girişli kullanıcı başkasının satırını okur/PATCH'ler | (hata yok, RLS) | 200 `[]` / 0 satır |

## İstemcinin revision kuralı (sözleşme)
`L` = istemcinin son gördüğü **sunucu** revision'ı. Her zaman sunucunun döndürdüğü değer kullanılır, gönderilen değer
değil:
- **Push:** upsert `POST /rest/v1/<oyun>_saves?on_conflict=user_id&select=revision` + `Prefer: resolution=merge-duplicates,return=representation`,
  gövdede `revision: L + 1` → cevap `[{"revision": n}]`, `L = n`. (Lenient satırda eşit revision kabul edildiğinde sunucu
  `eski + 1` yazar ve bunu döndürür; istemci böylece hiç geride kalmaz.)
- **Reset / restore:** `L` = RPC cevabındaki `revision` (satır yokken reset `0`). Restore'dan sonra satır yeniden çekilir (yukarıda).
- **Pull / benimseme (409 sonrası):** `L` = satırın `revision`'ı.
- Yerel kayıtlar ve çevrimdışı oynama `L`'yi değiştirmez. Bir sonraki yazma daima `L + 1`.

Doğrulanan davranış (SQL AO-V*, HTTP A6..A18):
- Normal push, reset ve restore sonrası `L + 1` kabul edilir.
- **İki cihaz:** A çevrimdışıyken `L` sabit kalır, B gerçek ilerleme yazar. A dönünce `L + 1` gönderir → 409, B'nin
  ilerlemesi korunur, A satırı çekip B'nin kaydını benimser. **Ezme yok** (SQL AO-V5/V6, HTTP A9..A11).
- Lenient satırda pull ile push arasına eski istemcinin (revision'sız) yazması girerse istemcinin revision'ı sunucudakine
  eşit olur → eski istemci yazması gibi kabul edilir (sunucu `+1`, satır lenient kalır; totalEarned düşüyorsa `stale_write`).
  Dönen revision okunduğu için istemci sonraki yazmada yeniden senkrondur. (Dönen değer okunmasaydı istemci kalıcı olarak
  bir geride kalırdı: SQL AO-V8/V9 bunu gösterir.) Tam koruma strict moddadır.

Kalan risk (Açık Ofis imzaları değiştirilmedi): **boşluklu revision kabulü.** Sunucu yalnız `revision > eski` ister;
`L`'si sunucudan büyük bir istemci (ör. misafir→giriş anında yerel kayıt kazanınca) yazarsa kabul edilir (SQL AO-V7).
"Tam olarak eski + 1" kuralı şimdilik önerilmez (bu yolu 409'a çevirir); gerekirse ayrı bir strict ayarı olabilir.

## Kodhane istemcisi (ayrı repo: thejackaltr/kodhane; bu işte DOKUNULMADI)
1. `cloud.js` `K.beforeReset`: `delete()` yerine `C.client.rpc('kodhane_reset_save', {})`; dönen `revision`'ı sakla.
   Migration'dan sonra eski DELETE 403 alır (satır kalır; eski istemcide sıfırlama bulut kaydını silemez, reconcile eski
   kaydı geri getirir: veri kaybı yok ama UX bozuk). Geri al: `kodhane_restore_save({p_backup_id})`, liste: `kodhane_list_save_backups()`.
2. `push()`: satıra `revision: L + 1`, `return=representation` + `select=revision` ile `L = dönen`; `remoteRow()`: `select('data, save_version, updated_at, revision, best_score, best_stage')`;
   409 → pull + benimse (Açık Ofis'teki gibi). Sıralama: `kodhane_leaderboard(p_limit, 'kodhane')` (imza aynı).
3. `game.js` sıfırlama onay metni (Frontend): "kalıcı olarak silinecek" yerine: ilerleme sıfırlanır; en iyi skor/aşama,
   sıralama ve takma ad kalır; bulutta 30 gün yedek; 10 sn "Geri al".
4. `data.revisions` bir oyun istatistiği; `revision` sütunuyla ilgisi yok.

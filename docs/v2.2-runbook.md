# v2.2 kayıt güvenliği — birleşik canlı uygulama runbook'u

**Hiçbir SQL, GM "1. aşama bitti" demeden ve Aryen uygulama onayı vermeden çalıştırılmaz.** Bu belge yer tutucu
bağlantılarla yazar (`$DB_URL`, `$API_URL`, `$ANON_KEY`, `$TEST_TOKEN`). Secret yazmayın; değerleri oturumda ortam
değişkeni olarak verin.

## Hedef
- **Tek veritabanı**, iki adres: `supabase.teserix.com` = `kodhane-api.teserix.com` (aynı DB, veri taşınmıyor).
- Hangi adresten bağlandığınız fark etmez. Uygulamadan önce hedefin doğru DB olduğunu (a) adımındaki sorgu doğrular.
- İki migration **aynı onayla, sabit sırayla** uygulanır:
  1. `supabase/migrations/20260928160000_v2_2_kodhane_save_safety.sql`
  2. `supabase/migrations/20260928160100_v2_2_acik_ofis_save_safety.sql`
- İkisinden sonra `kodhane_leaderboard` **v6**'da kalır (Açık Ofis dosyasındaki shim, Kodhane'den sonra geldiğinde
  v6'yı **ezmez**; dosya iki kez çalıştırılsa da v6 korunur — test: `u-M2`, `u-M3`, `u-H1`).

Yardımcı SQL (okuma amaçlı, ayrı çalıştırılabilir):
- `supabase/ops/v2_2_preflight.sql` — hedef doğrulama + parmak izi
- `supabase/ops/v2_2_fingerprint.sql` — yalnız parmak izi (uygulama öncesi / sonrası / geri alma sonrası `diff`)
- `supabase/ops/v2_2_leaderboard_snapshot.sql` — sıralama anlığı (öncesi / sonrası `diff`)
- `supabase/ops/v2_2_verify.sql` — şema, grant, backfill, v6 kontrolü (18/18)

**Uyarı:** v2.2'den sonra `kodhane-cloud/leaderboard.v5.sql` (ve v1–v4) **çalıştırılmaz**: sıralama tekrar anlık
`totalEarned`'e döner. `kodhane-cloud/leaderboard.sql` (v6) zararsızdır: sıralama fonksiyonuna dokunmaz.

### Yayın sırası
1. Bu runbook'un migration adımları (önce Kodhane, sonra Açık Ofis).
2. Açık Ofis v2.2 istemcisi **ve** Kodhane v4.2 istemcisi. Kodhane istemcisi **migration'la aynı gün** çıkmalı: DELETE
   yetkisi kalkıyor, eski "Kaydı sıfırla" (`DELETE`) 403 alır ve buluttaki kayıt silinmez (reconcile eski kaydı geri
   getirir → UX bozuk). v2.2 / v4.2 istemcileri `revision` ve `best_score` sütunlarını seçtiği için migration'dan önce
   çıkamaz (pull 400).
3. Eski (v2.1.x) cihazlar, bir satır bir kez v2.2 yazması veya reset gördükten sonra o hesap için 409 alır (güncelleyene
   kadar salt okunur). Lenient satırlarda eski istemci hâlâ yazabilir; strict moda geçiş (h) bunu kapatır.

### 2. / 3. aşama (şimdilik yok)
- **2. aşama:** Açık Ofis dosyası ileride kendi instance'ına olduğu gibi uygulanır; istemci o zaman
  `acik_ofis_leaderboard` / `acik_ofis_profiles`'a geçer. Bugün bu iki nesne dosyada oluşturulur ama **şimdilik
  kullanılmıyor** (v2.2 istemcisi `kodhane_leaderboard` + `kodhane_profiles` kullanmaya devam eder).
- **3. aşama:** Ortak DB'deki Açık Ofis parçaları, ayrı onayla temizlenir.

## (h) Ayrı adım: katı (strict) moda geçiş
- Ne zaman: v2.2 / v4.2 yayınından sonra, eski istemci yazmaları ihmal edilebilir düzeye inince (ayrı onay).
- Nasıl (oyun bağımsız; ikisini birden veya teker teker):
  ```sql
  update public.kodhane_game_config   set value = '"strict"', updated_at = now() where key = 'revision_mode';
  update public.acik_ofis_game_config set value = '"strict"', updated_at = now() where key = 'revision_mode';
  ```
- Etki: revision artırmayan her yazma 409 `stale_revision` → eski istemciler buluta kayıt yapamaz (kayıt korunur).
  Lenient dönemdeki "bir adım geride kalma" riski (istemci notları) kapanır.
- Geri alma: `value = '"lenient"'`. Satır bazında strict olmuş satırlar strict kalır (tasarım gereği).
